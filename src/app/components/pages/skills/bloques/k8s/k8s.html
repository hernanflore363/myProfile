03 · Componentes principales

Manifiestos ilustrativos válidos como base. Ajusta nombres, imágenes, puertos y recursos al entorno real. Normalmente se gestionan Pods mediante un Deployment, no creando Pods aislados.

Pod

Unidad de ejecución de uno o más contenedores que comparten red y volúmenes.

apiVersion: v1
  kind: Pod
  metadata:
    name: backend-pod
    labels:
      app: backend
  spec:
    containers:
      - name: backend
        image: nginx:1.27
        ports:
          - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "500m"
            memory: "128Mi"
        livenessProbe:
          httpGet:
            path: /
            port: 80
    restartPolicy: Always

Uso: pruebas y debugging; no suele ser el patrón de despliegue productivo.

Deployment

Administra réplicas de Pods y actualizaciones declarativas para aplicaciones stateless.

apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: backend
  spec:
    replicas: 3
    selector:
      matchLabels:
        app: backend
    template:
      metadata:
        labels:
          app: backend
      spec:
        containers:
          - name: backend
            image: nginx:1.27
            ports:
              - containerPort: 80
            resources:
              requests:
                cpu: "100m"
                memory: "64Mi"
              limits:
                cpu: "500m"
                memory: "128Mi"

Uso: APIs, frontends y servicios sin identidad persistente por Pod.

Service

Dirección estable que selecciona Pods mediante labels.

apiVersion: v1
  kind: Service
  metadata:
    name: backend-service
  spec:
    type: ClusterIP
    selector:
      app: backend
    ports:
      - name: http
        protocol: TCP
        port: 80
        targetPort: 80

Uso: comunicación interna; el selector debe coincidir con los labels de los Pods.

Ingress

Define reglas HTTP/HTTPS y requiere un Ingress Controller compatible. 

apiVersion: networking.k8s.io/v1
  kind: Ingress
  metadata:
    name: backend-ingress
  spec:
    ingressClassName: nginx
    rules:
      - host: api.example.com
        http:
          paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: backend-service
                  port:
                    number: 80

Uso: publicar rutas HTTP. TLS y anotaciones dependen del controlador.

ConfigMap

Almacena configuración no sensible fuera de la imagen.

apiVersion: v1
  kind: ConfigMap
  metadata:
    name: backend-config
  data:
    ENVIRONMENT: "development"
    LOG_LEVEL: "INFO"
    TIMEZONE: "America/La_Paz"

Uso: configuración por ambiente. No guardar contraseñas ni tokens aquí.

Secret

Almacena datos sensibles; Base64 no equivale a cifrado.

apiVersion: v1
  kind: Secret
  metadata:
    name: backend-secret
  type: Opaque
  stringData:
    username: "<replace-me>"
    password: "<replace-me>"

No guardar secretos reales en Git. Aplicar RBAC mínimo y cifrado en reposo según la plataforma.

PersistentVolumeClaim (PVC)

Solicita almacenamiento persistente, según la StorageClass disponible. 

apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: backend-data
  spec:
    accessModes:
      - ReadWriteOnce
    resources:
      requests:
        storage: 5Gi

Uso: datos que deben sobrevivir a la recreación del Pod, según el backend de almacenamiento.

StatefulSet

Gestiona Pods con identidad estable y almacenamiento dedicado por réplica si se configura.

apiVersion: apps/v1
  kind: StatefulSet
  metadata:
    name: database
  spec:
    serviceName: database-headless
    replicas: 1
    selector:
      matchLabels:
        app: database
    template:
      metadata:
        labels:
          app: database
      spec:
        containers:
          - name: database
            image: postgres:16
            ports:
              - containerPort: 5432
            volumeMounts:
              - name: data
                mountPath: /var/lib/postgresql/data
    volumeClaimTemplates:
      - metadata:
          name: data
        spec:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 10Gi

Uso: workloads con estado. En producción también requiere backups y una estrategia operativa.

05 · Kubectl Developer Cheat Sheet

Referencia práctica con el comando, qué hace, cuándo usarlo y qué debes tener en cuenta. Los ejemplos usan el namespace dev; cambia los nombres por los recursos reales de tu clúster.

Antes de ejecutar: confirma siempre el contexto con kubectl config current-context. Un comando correcto ejecutado contra el clúster equivocado puede afectar QA o producción. Los valores entre < > son marcadores: reemplázalos, no los copies literalmente.

A. Contexto, clúster y namespaces

El contexto indica a qué clúster y usuario se conecta kubectl. El namespace delimita dónde buscar o modificar recursos.

kubectl version
  kubectl config get-contexts
  kubectl config current-context
  kubectl config use-context <context-name>
  kubectl cluster-info
  kubectl get nodes
  kubectl get namespaces
  kubectl get pods -n dev
  kubectl config set-context --current --namespace=dev
kubectl version
Muestra la versión del cliente kubectl y, si es posible, la del servidor Kubernetes. Útil para detectar incompatibilidades de versión.
kubectl config get-contexts
Lista los contextos disponibles en tu kubeconfig. El asterisco señala el contexto actual.
kubectl config current-context
Muestra el contexto activo. Ejecútalo antes de aplicar, actualizar o borrar recursos.
kubectl config use-context <context-name>
Cambia el contexto activo al indicado. Sustituye el marcador por un nombre que aparezca en get-contexts.
kubectl cluster-info
Muestra direcciones de servicios centrales del clúster y ayuda a comprobar que el acceso funciona.
kubectl get nodes
Lista los nodos de cómputo y su estado. Normalmente requiere permisos a nivel de clúster.
kubectl get namespaces
Lista los namespaces, que separan recursos por entorno, equipo o aplicación.
kubectl get pods -n dev
Lista los Pods del namespace dev. El flag -n evita depender del namespace por defecto.
kubectl config set-context --current --namespace=dev
Establece dev como namespace predeterminado para el contexto actual. Es una comodidad local, no crea el namespace.

B. Inspeccionar recursos

Usa estos comandos para localizar la aplicación, revisar etiquetas y conocer la configuración efectiva.

kubectl get pods -n dev
  kubectl get pods -o wide -n dev
  kubectl get deployments -n dev
  kubectl get services -n dev
  kubectl get ingress -n dev
  kubectl get configmaps -n dev
  kubectl get secrets -n dev
  kubectl get deployments,services,ingress -n dev
  kubectl get pods --show-labels -n dev
  kubectl get pods -l app=backend -n dev
  kubectl get pod <pod-name> -o yaml -n dev
  kubectl get all -n dev
  kubectl describe pod <pod-name> -n dev
  kubectl get events --sort-by=.metadata.creationTimestamp -n dev
kubectl get pods
Lista los Pods y su estado, por ejemplo Running, Pending o CrashLoopBackOff.
-o wide
Añade columnas como nodo e IP del Pod; ayuda a investigar dónde se ejecuta.
get deployments / services / ingress
Muestra el estado deseado y disponible de los Deployments, los puntos de acceso internos de Services y las reglas HTTP/HTTPS de Ingress.
get configmaps / secrets
Lista objetos de configuración. Evita imprimir Secrets completos en terminales compartidas o logs.
get deployments,services,ingress
Consulta varios tipos de recursos en una sola ejecución.
--show-labels y -l app=backend
Muestra las etiquetas o filtra recursos por selector. Las etiquetas deben coincidir con las definidas en los manifiestos.
-o yaml
Imprime el objeto completo en YAML tal como está almacenado en el clúster, incluidos campos administrados por Kubernetes. No siempre es un manifiesto limpio para volver a versionar.
kubectl get all
Ofrece un resumen de varios recursos comunes, pero no incluye todos: consulta por separado Secrets, ConfigMaps, PVC e Ingress, entre otros.
kubectl describe pod
Presenta detalles, condiciones, contenedores, montajes y eventos asociados al Pod.
kubectl get events --sort-by=...
Ordena eventos por fecha de creación para ver advertencias recientes, como fallos al descargar imágenes o problemas de scheduling.

C. Crear, aplicar, escalar y reiniciar

# Crear un Deployment de ejemplo (no sustituye un manifiesto versionado)
  kubectl create deployment backend --image=my-registry/backend:v1 -n dev

  # Aplicar los manifiestos YAML de un archivo o directorio
  kubectl apply -f deployment.yaml -n dev
  kubectl apply -f ./k8s/ -n dev

  # Ver qué cambiaría antes de aplicarlo
  kubectl diff -f ./k8s/ -n dev

  # Esperar al resultado del despliegue y observar los Pods
  kubectl rollout status deployment/backend -n dev
  kubectl get pods -w -n dev

  # Ajustar el número de réplicas
  kubectl scale deployment/backend --replicas=3 -n dev

  # Reiniciar gradualmente los Pods del Deployment
  kubectl rollout restart deployment/backend -n dev
kubectl create deployment
Crea rápidamente un Deployment a partir de una imagen. Es práctico para pruebas; en proyectos reales suele convenir mantener el YAML en Git.
kubectl apply -f
Crea o actualiza recursos declarados en YAML. Kubernetes intenta hacer que el estado real coincida con la configuración deseada.
kubectl diff -f
Compara el manifiesto local con la configuración del clúster y muestra diferencias previstas; no aplica los cambios.
kubectl rollout status
Espera y muestra si el Deployment termina su actualización correctamente. Si no avanza, revisa Pods, eventos y logs.
kubectl get pods -w
Se queda observando cambios en tiempo real; pulsa Ctrl+C para salir.
kubectl scale
Cambia el número deseado de réplicas. La capacidad real también depende de recursos disponibles y políticas del clúster.
kubectl rollout restart
Provoca una recreación gradual de los Pods del Deployment. Puede servir para que la aplicación vuelva a cargar configuración montada; no actualiza por sí solo la imagen.

D. Actualizar imágenes y revertir despliegues

kubectl set image deployment/backend backend=my-registry/backend:v2 -n dev
  kubectl rollout status deployment/backend -n dev
  kubectl rollout history deployment/backend -n dev
  kubectl rollout history deployment/backend --revision=2 -n dev
  kubectl rollout undo deployment/backend -n dev
  kubectl rollout undo deployment/backend --to-revision=2 -n dev
  kubectl get deployment backend -o jsonpath='.spec.template.spec.containers[*].image' -n dev
kubectl set image
Cambia la imagen de un contenedor dentro del Deployment. En backend=..., el primer backend es el nombre del contenedor definido en el Pod template; puede ser distinto al nombre del Deployment.
rollout status
Comprueba que las nuevas réplicas estén listas y que la actualización avance.
rollout history
Lista las revisiones de rollout. Con --revision=2 muestra detalles de una revisión específica cuando existe.
rollout undo
Revierte el Deployment a una revisión anterior; con --to-revision=2 intenta volver a esa revisión concreta. Revisa el resultado después de revertir.
-o jsonpath=...
Extrae únicamente las imágenes configuradas, sin imprimir todo el objeto. Si hay varios contenedores, puede devolver varias imágenes.

Importante: la imagen debe existir en un registry accesible por los nodos y el clúster debe tener credenciales si el registry es privado. Preferí etiquetas inmutables o digest; reutilizar latest puede dificultar saber qué versión se ejecuta.

E. Logs y diagnóstico

kubectl logs <pod-name> -n dev
  kubectl logs <pod-name> -n dev --tail=100
  kubectl logs -f <pod-name> -n dev
  kubectl logs <pod-name> -n dev --since=10m
  kubectl logs <pod-name> -c <container-name> -n dev
  kubectl logs <pod-name> -n dev --previous
  kubectl logs deployment/backend -n dev --all-containers=true
  kubectl describe pod <pod-name> -n dev
  kubectl describe deployment backend -n dev
  kubectl get events --sort-by=.metadata.creationTimestamp -n dev
  kubectl top pods -n dev
  kubectl top nodes
kubectl logs
Muestra la salida estándar y de error del contenedor; empieza aquí cuando la API responde con errores o el proceso termina.
--tail=100 / --since=10m
Limita la salida a las últimas 100 líneas o a los últimos 10 minutos para evitar volcar demasiada información.
-f
Sigue los logs en tiempo real. Termina la lectura con Ctrl+C.
-c <container-name>
Selecciona un contenedor específico cuando el Pod tiene más de uno.
--previous
Consulta los logs de la instancia anterior del contenedor, si está disponible. Es especialmente útil con CrashLoopBackOff.
logs deployment/backend --all-containers=true
Recoge logs de los Pods asociados al Deployment e incluye todos sus contenedores; si el selector no identifica lo esperado, consulta directamente el Pod.
kubectl describe
Muestra configuración resumida y eventos relevantes para entender por qué un Pod no arranca o un Deployment no progresa.
kubectl top pods / nodes
Muestra uso actual de CPU y memoria. Requiere Metrics Server (u otra integración compatible) y permisos adecuados.

F. Entrar en un contenedor y ejecutar comandos

kubectl exec -it <pod-name> -n dev -- /bin/sh
  kubectl exec -it <pod-name> -c <container-name> -n dev -- /bin/sh
  kubectl exec <pod-name> -n dev -- printenv
  kubectl exec <pod-name> -n dev -- ls -la /app
kubectl exec -it ... -- /bin/sh
Abre una shell interactiva dentro del contenedor para inspeccionar archivos o procesos. -i mantiene la entrada abierta; -t asigna una terminal; -- separa los argumentos de kubectl del comando remoto.
-c <container-name>
Selecciona el contenedor correcto dentro de un Pod multi-contenedor.
printenv / ls -la /app
Ejecuta un comando y sale; permite revisar variables o archivos sin abrir una shell. No compartas la salida de variables que puedan contener secretos.

Algunas imágenes mínimas no incluyen /bin/sh, Bash, curl ni herramientas de diagnóstico. En ese caso usa logs, eventos o un contenedor de depuración aprobado por tu equipo.

G. Port forwarding y pruebas de API

# Reenvía localhost:8080 al puerto 80 del Service
  kubectl port-forward service/backend-service 8080:80 -n dev

  # O directamente al puerto del Pod
  kubectl port-forward pod/<pod-name> 8080:8080 -n dev

  # En otra terminal, probar endpoints
  curl -i http://localhost:8080/health
  curl -i http://localhost:8080/api/users

  # Petición POST con JSON válido
  curl -X POST http://localhost:8080/api/users \
    -H "Content-Type: application/json" \
    -d '"name":"Hernan"'
kubectl port-forward service/backend-service 8080:80
Abre un túnel temporal desde el puerto local 8080 al puerto 80 del Service. El formato es PUERTO_LOCAL:PUERTO_REMOTO; el Service debe existir en el namespace indicado.
kubectl port-forward pod/...
Envía tráfico directamente a un Pod, útil para aislar una prueba del Service o Ingress.
curl -i
Hace una petición HTTP y muestra también los encabezados de respuesta, incluido el código HTTP.
curl -X POST ... -H ... -d ...
Envía una petición POST con el encabezado que declara JSON y un cuerpo JSON válido. Ajusta ruta, autenticación y estructura según la API real.

Mantén abierta la terminal donde corre port-forward mientras pruebas desde otra terminal. Al pulsar Ctrl+C, el túnel se cierra.

H. Namespaces, ConfigMaps y Secrets

kubectl create namespace dev
  kubectl get pods -n dev
  kubectl create configmap backend-config --from-literal=LOG_LEVEL=DEBUG -n dev
  kubectl describe configmap backend-config -n dev
  kubectl create secret generic backend-secret --from-literal=API_KEY='<your-api-key>' -n dev
  kubectl describe secret backend-secret -n dev
  kubectl get configmaps,secrets -n dev
kubectl create namespace dev
Crea un namespace para agrupar recursos. Si ya existe, el comando puede informar que el recurso ya existe.
kubectl create configmap ... --from-literal
Crea un ConfigMap con pares clave/valor no confidenciales, por ejemplo el nivel de logs. La aplicación debe referenciarlo como variable de entorno o volumen para utilizarlo.
kubectl create secret generic ...
Crea un Secret para datos sensibles. El texto de ejemplo es un marcador, no una credencial real. Los argumentos pueden quedar registrados en el historial del shell; para secretos reales prefiere el mecanismo aprobado por tu organización.
kubectl describe configmap/secret
Muestra metadatos y detalles del recurso. Aun así, evita exponer datos sensibles en capturas, logs o sesiones compartidas.

Seguridad: Base64 no es cifrado. Restringe el acceso con RBAC, habilita cifrado en reposo cuando corresponda y no guardes credenciales reales en Git.

I. Ayuda, validación y limpieza

kubectl api-resources
  kubectl explain deployment
  kubectl explain deployment.spec
  kubectl apply --dry-run=client -f deployment.yaml
  kubectl diff -f ./k8s/ -n dev
  kubectl delete pod <pod-name> -n dev
  kubectl delete deployment backend -n dev
  kubectl delete -f deployment.yaml -n dev
  kubectl delete namespace dev
kubectl api-resources
Lista los tipos de recursos que la API de este clúster reconoce, incluidos sus nombres abreviados y si son namespaced.
kubectl explain deployment
Muestra la documentación de campos de un recurso. Añade rutas como deployment.spec para explorar sus propiedades.
--dry-run=client
Valida y procesa el manifiesto localmente sin crear ni modificar recursos en el clúster. No sustituye todas las validaciones del servidor.
kubectl delete pod
Borra un Pod concreto. Si pertenece a un Deployment, ReplicaSet u otro controlador, normalmente se creará un reemplazo para mantener el estado deseado.
kubectl delete deployment
Elimina el Deployment y los Pods que administra; puede interrumpir el servicio si no existen otras réplicas o controladores.
kubectl delete -f
Elimina los recursos declarados en el archivo indicado. Revisa cuidadosamente el archivo y el namespace antes de ejecutar.
kubectl delete namespace dev
Elimina el namespace y los recursos que contiene. Es una operación destructiva; no la uses como limpieza rutinaria sin autorización y revisión.

J. Flujo diario recomendado para una API

Secuencia sugerida para revisar el contexto, aplicar cambios, comprobar el rollout y diagnosticar errores.


                # 1. Confirmar destino
                kubectl config current-context
                kubectl get nodes

                # 2. Localizar los recursos de la API
                kubectl get deployments,pods,services -n dev

                # 3. Revisar cambios antes de aplicarlos
                kubectl diff -f ./k8s/ -n dev

                # 4. Aplicar los manifiestos
                kubectl apply -f ./k8s/ -n dev

                # 5. Esperar y comprobar el estado
                kubectl rollout status deployment/backend -n dev
                kubectl get pods -o wide -n dev

                # 6. Si falla, revisar detalles y logs
                kubectl describe pod <pod-name> -n dev
                kubectl logs <pod-name> -n dev --tail=100

                # 7. Probar la API mediante un túnel temporal
                kubectl port-forward service/backend-service 8080:80 -n dev
                # En otra terminal:
                curl -i http://localhost:8080/health

                # 8. Si procede, revisar historial y revertir
                kubectl rollout history deployment/backend -n dev
                kubectl rollout undo deployment/backend -n dev

Resumen de flags frecuentes: -n selecciona namespace; -o wide agrega columnas; -o yaml imprime YAML; -f indica archivo/directorio; -l filtra por etiquetas; -w observa cambios; -c elige contenedor; --previous solicita logs de la instancia anterior.

Sustituye dev, backend, backend-service y los nombres de contenedor por los reales. En entornos compartidos, respeta permisos y procesos de cambio antes de actualizar o eliminar recursos.

06 · Troubleshooting rápido

Estado Qué revisar Primeros pasos
CrashLoopBackOff El contenedor falla repetidamente. logs --previous, describe pod, probes y configuración.
ImagePullBackOff No puede descargar la imagen. Nombre/tag, registry y credenciales.
Pending Pod sin asignación o preparación. Eventos, recursos, afinidad, taints y PVC.
OOMKilled Consumo de memoria excedido. Consumo real, límites y requests.
CreateContainerConfigError Configuración del contenedor inválida. Claves y referencias a ConfigMaps/Secrets.
Service sin tráfico No encuentra endpoints saludables. Selector, labels y readinessProbe.

07 · Buenas prácticas para producción

Operación y resiliencia

  • ✓ Usa Deployments para servicios stateless.
  • ✓ Define requests, limits y probes apropiadas.
  • ✓ Usa readinessProbe para controlar cuándo recibir tráfico.
  • ✓ Observa logs, métricas, eventos y alertas.
  • ✓ Planifica réplicas y estrategia de rollout.

Seguridad y cambios

  • ✓ Aplica RBAC con privilegios mínimos.
  • ✓ No guardes credenciales reales en Git.
  • ✓ Base64 no es cifrado.
  • ✓ Usa imágenes versionadas y escaneadas.
  • ✓ Revisa diff, contexto y namespace antes de aplicar o borrar.

09 · Instalar Kong para un laboratorio

Paso 1. Instalar el chart oficial

Este método instala Kong Gateway y Kong Ingress Controller usando el chart wrapper kong/ingress. La configuración por defecto puede variar entre versiones del chart; fija una versión aprobada en entornos compartidos.

helm repo add kong https://charts.konghq.com
  helm repo update
  helm upgrade --install kong kong/ingress \\
    --namespace kong --create-namespace

  # Espera a que estén listos los Pods
  kubectl get pods -n kong -w

Si la empresa ya administra Kong, no ejecutes este paso: solicita el nombre de la clase Ingress, el namespace de Kong y el endpoint de entrada. Para personalizar el chart, crea un values.yaml revisado por el equipo de plataforma.

Paso 2. Inspeccionar la instalación

helm list -n kong
  kubectl get deployments,services -n kong
  kubectl get ingressclass
  kubectl get pods -n kong -o wide
  kubectl describe ingressclass kong

Busca la clase kong y el Service de proxy. Si no existe la clase, no continúes suponiendo que el controlador la atenderá: revisa los valores de instalación y la versión de KIC con el administrador.

10 · Crear la API y publicar una ruta

Guarda los siguientes archivos en una carpeta k8s/. El backend de demostración usa hashicorp/http-echo para devolver texto sin necesidad de crear una aplicación Node.js. En un proyecto real, reemplaza la imagen y el puerto por los de tu API.

Archivo 1 — 00-namespace.yaml

apiVersion: v1
  kind: Namespace
  metadata:
    name: demo
    labels:
      app.kubernetes.io/part-of: kong-demo

Crea un espacio lógico para aislar los recursos de este tutorial. El controlador Kong puede estar en el namespace kong, mientras la aplicación vive en demo.

Archivo 2 — 10-deployment.yaml

apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: echo-api
    namespace: demo
    labels:
      app: echo-api
  spec:
    replicas: 2
    selector:
      matchLabels:
        app: echo-api
    template:
      metadata:
        labels:
          app: echo-api
      spec:
        containers:
          - name: echo
            image: hashicorp/http-echo:1.0.0
            args:
              - "-listen=:5678"
              - "-text=Hola desde el backend detrás de Kong"
            ports:
              - name: http
                containerPort: 5678
            readinessProbe:
              tcpSocket:
                port: 5678
              initialDelaySeconds: 2
              periodSeconds: 5
            livenessProbe:
              tcpSocket:
                port: 5678
              initialDelaySeconds: 5
              periodSeconds: 10
            resources:
              requests:
                cpu: 50m
                memory: 32Mi
              limits:
                cpu: 250m
                memory: 64Mi

Deployment mantiene dos réplicas. Las probes TCP verifican que el puerto acepte conexiones; para una API real, prefiere endpoints de salud HTTP si la aplicación los ofrece. Los recursos son valores ilustrativos.

Archivo 3 — 20-service.yaml

apiVersion: v1
  kind: Service
  metadata:
    name: echo-api
    namespace: demo
  spec:
    type: ClusterIP
    selector:
      app: echo-api
    ports:
      - name: http
        port: 80
        targetPort: http

El Service expone el puerto 80 dentro del clúster y lo dirige al puerto nombrado http del contenedor (5678). Kong enruta al Service, no directamente a una IP de Pod.

Archivo 4 — 30-ingress.yaml

apiVersion: networking.k8s.io/v1
  kind: Ingress
  metadata:
    name: echo-api
    namespace: demo
  spec:
    ingressClassName: kong
    rules:
      - host: echo.local
        http:
          paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: echo-api
                  port:
                    number: 80

Declara la regla de host y ruta. KIC detecta el Ingress y configura Kong Gateway. El host echo.local es de prueba; no crea DNS público ni un balanceador por sí solo.

Aplicar y comprobar los manifiestos

kubectl apply -f k8s/00-namespace.yaml
  kubectl apply -f k8s/10-deployment.yaml
  kubectl apply -f k8s/20-service.yaml
  kubectl apply -f k8s/30-ingress.yaml

  kubectl rollout status deployment/echo-api -n demo
  kubectl get pods,svc,ingress -n demo
  kubectl describe ingress echo-api -n demo

También puedes ejecutar kubectl apply -f k8s/ si todos los archivos están dentro de esa carpeta. Separa manifiestos por responsabilidad para que sea más fácil revisarlos y versionarlos.

11 · Añadir un plugin de Kong: rate limiting

El siguiente ejemplo limita a cinco solicitudes por minuto en cada instancia de Kong cuando se utiliza la política local. Es para aprender, no una cuota global exacta en un despliegue con varias réplicas de Gateway.

Archivo 5 — 40-kong-plugin.yaml

apiVersion: configuration.konghq.com/v1
  kind: KongPlugin
  metadata:
    name: echo-rate-limit
    namespace: demo
    annotations:
      kubernetes.io/ingress.class: kong
  plugin: rate-limiting
  config:
    minute: 5
    policy: local

El recurso KongPlugin define el plugin y sus parámetros. La anotación siguiente vincula el plugin al Ingress. Comprueba que la versión instalada de KIC soporte esta API y este tipo de recurso.

Actualizar 30-ingress.yaml

apiVersion: networking.k8s.io/v1
  kind: Ingress
  metadata:
    name: echo-api
    namespace: demo
    annotations:
      konghq.com/plugins: echo-rate-limit
  spec:
    ingressClassName: kong
    rules:
      - host: echo.local
        http:
          paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: echo-api
                  port:
                    number: 80
kubectl apply -f k8s/40-kong-plugin.yaml
  kubectl apply -f k8s/30-ingress.yaml
  kubectl get kongplugin -n demo
  kubectl describe kongplugin echo-rate-limit -n demo

Para una cuota compartida entre múltiples Pods de Kong, evalúa la política Redis y su configuración segura. No pongas contraseñas reales directamente en el manifiesto.

12 · Probar el recorrido de la petición

Opción A — Port-forward al Service proxy de Kong

# Terminal 1: consulta el nombre real del Service de Kong
  kubectl get svc -n kong

  # Si se llama kong-gateway-proxy, abre el túnel
  kubectl port-forward -n kong svc/kong-gateway-proxy 8000:80

Deja ese comando ejecutándose. Si el Service tiene otro nombre o no expone el puerto 80, adapta el comando según kubectl get svc -n kong.

Opción B — Enviar una petición con el host de la ruta

# En otra terminal, especifica el host que espera el Ingress
  curl -i -H 'Host: echo.local' http://127.0.0.1:8000/

  # Repite varias solicitudes para observar el rate limit
  for i in $(seq 1 7); do
    curl -s -o /dev/null -w '%http_code\n' \\
      -H 'Host: echo.local' http://127.0.0.1:8000/
  done

La respuesta esperada inicial es HTTP 200 con el texto del backend. Con el plugin aplicado y el límite local alcanzado, algunas solicitudes posteriores deben recibir HTTP 429. Si no ocurre, revisa los logs de KIC y Kong y confirma que el plugin esté vinculado al Ingress correcto.

13 · HTTPS/TLS: qué falta para producción

El tutorial anterior usa HTTP para que puedas probar la ruta localmente. Para HTTPS, necesitas un certificado y una clave válidos (o un Secret generado por cert-manager) y debes definir dónde termina TLS: en el WAF/balanceador externo, en Kong Gateway, o en ambos con TLS hacia el backend según la política de la empresa.

# Ejemplo: crear un Secret TLS a partir de archivos reales
  # No subas tls.key a Git ni compartas la clave privada.
  kubectl create secret tls echo-tls \\
    --cert=./tls.crt \\
    --key=./tls.key \\
    -n demo

Después, agrega una sección spec.tls al Ingress con el host y el nombre del Secret, y confirma que el listener de Kong y la exposición externa soporten HTTPS. El certificado del ejemplo debe corresponder al dominio que utilices.

spec:
    ingressClassName: kong
    tls:
      - hosts:
          - api.ejemplo.com
        secretName: echo-tls
    rules:
      - host: api.ejemplo.com
        http:
          paths:
            - path: /
              pathType: Prefix
              backend:
                service:
                  name: echo-api
                  port:
                    number: 80

El fragmento TLS se integra en el mismo Ingress completo; no lo apliques como un manifiesto separado que contenga solo spec.

14 · Flujo de trabajo recomendado

  1. Confirmar contexto y permisos de Kubernetes.
  2. Confirmar con plataforma que Kong Gateway y KIC están instalados y cuál es la IngressClass correcta.
  3. Versionar Deployment, Service, Ingress y KongPlugin en Git.
  4. Revisar los YAML con el equipo y ejecutar kubectl diff -f k8s/.
  5. Aplicar los manifiestos mediante el pipeline aprobado.
  6. Verificar rollout, endpoints, rutas, plugins y logs.
  7. En producción, configurar DNS, TLS, WAF y balanceador según la arquitectura corporativa, no con valores de laboratorio.
