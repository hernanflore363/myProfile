Argo CD – GitOps Architecture

Guía práctica de Argo CD para implementar GitOps, automatización de despliegues y sincronización continua de aplicaciones Kubernetes.

Application

Recurso principal de Argo CD. Define qué aplicación desplegar, desde qué repositorio y en qué cluster y namespace de Kubernetes.

``` 

apiVersion: argoproj.io/v1alpha1
kind: Application

metadata:
  name: backend-api

spec:

  project: default

  source:
    repoURL: https://github.com/example/gitops
    targetRevision: main
    path: apps/backend

  destination:
    server: https://kubernetes.default.svc
    namespace: backend

  syncPolicy:
    automated:
      prune: true
      selfHeal: true

    syncOptions:
      - CreateNamespace=true
``` Use: definir una aplicación GitOps

Git Repository

Git actúa como fuente de verdad. Contiene los manifiestos Kubernetes que representan el estado deseado.

``` 

gitops/
│
├── apps/
│   └── backend/
│       ├── deployment.yaml
│       ├── service.yaml
│       └── ingress.yaml
│
└── environments/
    ├── development/
    ├── staging/
    └── production/
``` Use: fuente de verdad del sistema

Sync

Sincroniza el estado definido en Git con el estado real existente en Kubernetes.

``` 

# Login

argocd login argocd-server

# Ver aplicaciones

argocd app list

# Sincronizar

argocd app sync backend-api

# Ver estado

argocd app get backend-api
``` Use: desplegar cambios

Automated Sync

Permite que Argo CD detecte cambios en Git y sincronice automáticamente Kubernetes.

``` 

syncPolicy:

  automated:

    prune: true

    selfHeal: true
``` Use: Continuous Deployment

Project

Permite agrupar aplicaciones y controlar qué repositorios, clusters y namespaces pueden utilizar.

``` 

apiVersion: argoproj.io/v1alpha1
kind: AppProject

metadata:
  name: financial-platform

spec:

  sourceRepos:
    - https://github.com/example/*

  destinations:

    - namespace: payments
      server: https://kubernetes.default.svc

    - namespace: accounts
      server: https://kubernetes.default.svc

  clusterResourceWhitelist:

    - group: "*"
      kind: "*"
``` Use: gobierno y control de aplicaciones

Repository

Argo CD puede conectarse a repositorios Git privados para obtener manifiestos y configuraciones.

``` 

argocd repo add \
  https://github.com/example/private-gitops \
  --username developer \
  --password ********
``` Use: integración con Git privado

Helm

Argo CD puede desplegar aplicaciones Kubernetes utilizando Helm Charts.

``` 

spec:

  source:

    repoURL:
      https://github.com/example/charts

    path:
      backend

    helm:

      valueFiles:
        - values-production.yaml
``` Use: parametrización de despliegues

Kustomize

Permite administrar diferentes ambientes utilizando overlays sobre una configuración base.

``` 

apps/
│
├── base/
│   ├── deployment.yaml
│   └── service.yaml
│
└── overlays/
    │
    ├── development/
    │   └── kustomization.yaml
    │
    ├── staging/
    │   └── kustomization.yaml
    │
    └── production/
        └── kustomization.yaml
``` Use: múltiples ambientes

Rollback

Permite regresar una aplicación a una versión anterior registrada en el historial de despliegues.

``` 

# Ver historial

argocd app history backend-api

# Rollback

argocd app rollback backend-api 5

# Ver estado

argocd app get backend-api
``` Use: recuperación ante despliegues fallidos

RBAC

Controla qué usuarios y equipos pueden administrar aplicaciones dentro de Argo CD.

``` 

policy.csv:

p, role:developer, applications,
  get, financial/*, allow

p, role:developer, applications,
  sync, financial/*, allow

p, role:developer, applications,
  delete, financial/*, deny

g, developer, role:developer
``` Use: seguridad y gobierno

GitOps Architecture Flow

  • Developer → Git Push
  • Git → Source of Truth
  • Argo CD → Detecta cambios
  • Argo CD → Compara Desired State vs Live State
  • Argo CD → Sync
  • Kubernetes → Aplica cambios
  • Argo CD → Health / Sync Status

Best Practices

  • ✔ Git debe ser la fuente de verdad
  • ✔ Separar configuración por ambientes
  • ✔ Utilizar AppProjects para gobierno
  • ✔ Habilitar selfHeal cuando corresponda
  • ✔ Utilizar prune con control
  • ✔ Implementar RBAC
  • ✔ No almacenar secrets directamente en Git
  • ✔ Utilizar Helm o Kustomize para parametrización
  • ✔ Mantener historial de cambios mediante Git
  • ✔ Separar repositorio de aplicación y configuración GitOps
