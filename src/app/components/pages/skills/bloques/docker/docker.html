Docker Architecture – Production Guide

Guía práctica de Docker para construir, ejecutar, conectar, persistir, diagnosticar y distribuir aplicaciones contenerizadas. Cada comando incluye qué hace, cuándo usarlo y qué debes revisar.

1. Conceptos fundamentales

Dockerfile

Receta declarativa con las instrucciones para construir una imagen. Docker ejecuta sus pasos durante el build.

  FROM node:22-alpine
  WORKDIR /app
  COPY package*.json ./
  RUN npm ci
  COPY . .
  EXPOSE 3000
  CMD ["npm", "start"]
  • FROM: imagen base con Node.js.
  • WORKDIR: directorio de trabajo dentro de la imagen.
  • COPY package*.json: copia los manifiestos de dependencias; ayuda a aprovechar la caché.
  • RUN npm ci: instala exactamente lo definido en package-lock.json; requiere ese archivo.
  • COPY . .: copia el código restante, salvo lo excluido por .dockerignore.
  • EXPOSE: documenta el puerto esperado; no publica el puerto en el host.
  • CMD: comando por defecto al iniciar el contenedor.

Image (imagen)

Plantilla versionada que contiene aplicación, runtime y dependencias. Una imagen no es el proceso que está ejecutándose.

  docker build -t my-api:v1 .
  docker images
  docker image inspect my-api:v1

build crea la imagen a partir del Dockerfile; -t asigna nombre y etiqueta; el punto indica el contexto de construcción actual. images lista imágenes locales. inspect muestra metadatos detallados.

Container (contenedor)

Instancia ejecutable de una imagen: proceso aislado con filesystem, red y ciclo de vida propios. Los datos escritos solo en su capa pueden perderse al eliminarlo.

  docker run -d --name my-api -p 3000:3000 my-api:v1
  docker ps
  docker logs -f my-api
  docker stop my-api

-d ejecuta en segundo plano; --name asigna un nombre; -p 3000:3000 publica puerto_host:puerto_contenedor. ps lista contenedores activos; logs -f sigue los logs; stop solicita detenerlo.

Volume (volumen)

Almacenamiento administrado por Docker y separado del ciclo de vida del contenedor. Se usa para datos que deben persistir, como los de una base de datos.

  docker volume create mysql_data
  docker volume ls
  docker volume inspect mysql_data

Un volumen sobrevive a la eliminación del contenedor. El comando -v mysql_data:/var/lib/mysql monta el volumen en el directorio de datos de MySQL. Elimina volúmenes solo si confirmaste que no necesitas su contenido.

Network (red)

Permite la comunicación entre contenedores. En una red definida por el usuario, normalmente se pueden resolver entre sí por nombre de contenedor o servicio.

  docker network create backend-network
  docker network ls
  docker network inspect backend-network

Conecta servicios a una red compartida. Desde la API, la base de datos se puede alcanzar usando el nombre DNS del servicio, por ejemplo mysql:3306, no localhost:3306.

Docker Compose

Define varios servicios, redes, volúmenes y configuración en un archivo YAML para administrarlos como una aplicación.

  docker compose up -d
  docker compose ps
  docker compose logs -f
  docker compose down

up -d crea/inicia los servicios en segundo plano; ps muestra su estado; logs -f sigue sus logs; down detiene y elimina contenedores y redes creados por Compose. Los volúmenes nombrados no se eliminan por defecto.

Registry

Servicio que almacena y distribuye imágenes, público o privado. Ejemplos: Docker Hub, GitLab Container Registry y registries de nube.

  docker login
  # Ajustar al registry y usuario reales
  docker tag my-api:v1 usuario/my-api:v1
  docker push usuario/my-api:v1
  docker pull usuario/my-api:v1

tag asigna otra referencia a la imagen local; push la publica; pull la descarga. El destino debe existir o permitir su creación y tu usuario debe tener permisos.

Healthcheck

Define una prueba periódica para marcar un contenedor como healthy o unhealthy. No reinicia por sí solo un proceso solo porque esté unhealthy.

  HEALTHCHECK --interval=30s --timeout=5s --retries=3 \\
    CMD wget --spider -q http://localhost:3000/health || exit 1

La ruta debe existir y la imagen debe incluir wget (o reemplazarlo por una herramienta disponible). Ajusta el puerto y endpoint a tu API.

Multi-stage build

Usa etapas separadas para compilar y ejecutar. Permite no copiar compiladores y herramientas de build a la imagen final.

  FROM golang:1.24 AS builder
  WORKDIR /src
  COPY . .
  RUN go build -o /out/api .

  FROM alpine:3.22
  WORKDIR /app
  COPY --from=builder /out/api ./api
  EXPOSE 8080
  CMD ["./api"]

La imagen final contiene el binario, no el toolchain completo. Para producción valida compatibilidad de bibliotecas, certificados CA, usuario no root y versiones soportadas.

2. Docker Developer Command Cheat Sheet

Comandos de uso frecuente, con explicación de su función y ejemplos para desarrollo y diagnóstico.

2.1 Verificar instalación y contexto

  docker --version
  docker version
  docker info
  docker context ls
  docker context show
  docker context use default
  • docker --version: muestra la versión del cliente.
  • docker version: muestra versiones del cliente y del daemon; ayuda a detectar problemas de conexión.
  • docker info: presenta datos del daemon, almacenamiento, runtime y configuración.
  • docker context ls/show/use: lista, identifica y cambia el destino al que se conecta Docker. Antes de operar, confirma que sea el entorno correcto.

2.2 Imágenes: construir, listar y eliminar

  docker build -t my-api:v1 .
  docker build --no-cache -t my-api:debug .
  docker images
  docker image history my-api:v1
  docker image inspect my-api:v1
  docker image rm my-api:v1
  docker image prune
  • build -t: construye una imagen etiquetada; . es el contexto que Docker puede leer.
  • --no-cache: rehace las capas sin usar caché; útil para investigar builds, pero suele tardar más.
  • images: lista las imágenes locales.
  • history: muestra las capas e instrucciones que contribuyeron a la imagen; no debe usarse para ocultar secretos incluidos por error.
  • inspect: muestra configuración detallada en formato JSON.
  • image rm: elimina una referencia local si no está en uso.
  • image prune: elimina imágenes dangling no utilizadas; revisa el alcance antes de limpiar.

2.3 Contenedores: ciclo de vida

  docker run --name my-api -d -p 3000:3000 my-api:v1
  docker ps
  docker ps -a
  docker start my-api
  docker stop my-api
  docker restart my-api
  docker rm -f my-api
  docker container prune
  • run: crea e inicia un contenedor nuevo a partir de una imagen.
  • ps: muestra contenedores activos; ps -a también incluye detenidos.
  • start/stop/restart: inicia, detiene o reinicia un contenedor ya creado.
  • rm -f: fuerza la eliminación del contenedor, incluso si está en ejecución; úsalo con cuidado.
  • container prune: elimina todos los contenedores detenidos. No elimina volúmenes por defecto.

2.4 Logs, estado y diagnóstico

  docker logs my-api
  docker logs -f --tail=100 my-api
  docker inspect my-api
  docker stats
  docker events
  docker top my-api
  • logs: consulta la salida estándar y errores del proceso; -f sigue la salida y --tail=100 limita las líneas iniciales.
  • inspect: revisa estado, puertos, variables, montajes y configuración; evita compartir su salida sin revisar datos sensibles.
  • stats: muestra consumo de CPU, memoria, red e I/O en tiempo real.
  • events: muestra eventos del daemon Docker.
  • top: muestra procesos que corren dentro del contenedor.

2.5 Entrar al contenedor y ejecutar comandos

  docker exec -it my-api sh
  docker exec my-api printenv
  docker exec -it my-api node --version
  docker cp my-api:/app/log.txt ./log.txt
  • exec -it ... sh: abre una shell interactiva dentro de un contenedor activo. Algunas imágenes mínimas no tienen sh o bash.
  • printenv: imprime variables de entorno; puede revelar secretos, así que no pegues la salida en tickets públicos.
  • node --version: ejecuta un comando dentro del contenedor sin abrir una shell.
  • cp: copia un archivo entre contenedor y host. No es un reemplazo de volúmenes para persistencia.

2.6 Puertos y redes

  docker port my-api
  docker network ls
  docker network create app-net
  docker network connect app-net my-api
  docker network inspect app-net
  docker network disconnect app-net my-api
  • port: muestra los mapeos de puertos publicados.
  • network ls/create: lista o crea redes.
  • network connect/disconnect: conecta o desconecta un contenedor de una red existente.
  • network inspect: permite verificar qué contenedores están conectados y la configuración de la red.

2.7 Volúmenes y datos

  docker volume create app-data
  docker volume ls
  docker volume inspect app-data
  docker run -d --name db -v app-data:/var/lib/mysql mysql:8.4
  docker volume rm app-data
  • create/ls/inspect: crean, listan e inspeccionan volúmenes.
  • -v app-data:/var/lib/mysql: monta el volumen nombrado en la ubicación de datos de MySQL.
  • volume rm: elimina un volumen; Docker normalmente impide borrar uno que esté en uso. Verifica respaldos antes de borrarlo.

Nota: no uses una contraseña real directamente en la línea de comandos ni la guardes en el historial. En producción utiliza un gestor de secretos y una política segura de credenciales.

2.8 Registry: publicar y descargar imágenes

  docker login registry.example.com
  docker tag my-api:v1 registry.example.com/team/my-api:v1
  docker push registry.example.com/team/my-api:v1
  docker pull registry.example.com/team/my-api:v1
  docker logout registry.example.com
  • login: autentica con el registry indicado.
  • tag: añade una referencia que incluye registry, proyecto, imagen y etiqueta.
  • push/pull: publica/descarga la imagen.
  • logout: cierra la sesión local del registry.

2.9 Limpieza segura

  docker system df
  docker container prune
  docker image prune
  docker builder prune
  docker system prune
  • system df: informa cuánto espacio usa Docker.
  • container prune: elimina contenedores detenidos.
  • image prune: elimina imágenes dangling no utilizadas.
  • builder prune: elimina caché de construcción que ya no se necesita.
  • system prune: limpia recursos no utilizados; lee la confirmación y revisa qué se eliminará. No agregues --volumes sin confirmar que los datos son prescindibles.

3. Docker Compose: API + MySQL

Ejemplo de desarrollo local. La API y MySQL comparten una red creada por Compose; el nombre del servicio mysql funciona como hostname desde la API.

compose.yaml

  services:
    api:
      build: .
      ports:
        - "3000:3000"
      environment:
        DB_HOST: mysql
        DB_PORT: "3306"
        DB_NAME: appdb
        DB_USER: appuser
        # Para desarrollo: cargar el valor desde un entorno local seguro
        DB_PASSWORD: DB_PASSWORD:?Define DB_PASSWORD en tu entorno
      depends_on:
        mysql:
          condition: service_healthy

    mysql:
      image: mysql:8.4
      environment:
        MYSQL_DATABASE: appdb
        MYSQL_USER: appuser
        MYSQL_PASSWORD: DB_PASSWORD:?Define DB_PASSWORD en tu entorno
        MYSQL_ROOT_PASSWORD: MYSQL_ROOT_PASSWORD:?Define MYSQL_ROOT_PASSWORD
      volumes:
        - mysql_data:/var/lib/mysql
      healthcheck:
        test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1"]
        interval: 10s
        timeout: 5s
        retries: 5

  volumes:
    mysql_data:

Compose interpreta las variables del host al procesar el archivo. Define DB_PASSWORD y MYSQL_ROOT_PASSWORD en tu entorno local o en un archivo ignorado por Git. Para producción, usa el mecanismo de secretos de la plataforma y revisa la seguridad de la configuración.

Comandos para administrarlo

  docker compose config
  docker compose up -d --build
  docker compose ps
  docker compose logs -f api
  docker compose exec api sh
  docker compose restart api
  docker compose down
  • config: valida y muestra la configuración ya interpolada; cuidado, puede mostrar valores sensibles.
  • up -d --build: construye las imágenes que corresponda y levanta los servicios en segundo plano.
  • ps: estado de servicios y contenedores.
  • logs -f api: sigue logs de la API.
  • exec api sh: abre una shell en el servicio si la imagen contiene una shell.
  • restart api: reinicia solo el servicio API.
  • down: detiene y elimina contenedores y red del proyecto; el volumen nombrado permanece si no se usa -v.

4. Flujo real de desarrollo y entrega

  1. Preparar el proyecto. Tener Dockerfile, .dockerignore y dependencias bloqueadas en el repositorio.
  2. Construir imagen. docker build -t my-api:dev . empaqueta código y runtime; el tag ayuda a identificar la versión.
  3. Probar localmente. docker run --rm --name my-api-test -p 3000:3000 my-api:dev. --rm elimina el contenedor cuando termina, pero no la imagen.
  4. Revisar logs y salud. Usar docker logs, docker ps e inspeccionar el endpoint desde el host.
  5. Ejecutar dependencias. En proyectos con varias piezas, definir API, base de datos, redes y volúmenes en Compose.
  6. Etiquetar y publicar. Usar un registry accesible por el entorno destino; emplear una etiqueta de versión o un identificador de commit, no depender de latest.
  7. Desplegar. Un entorno de Kubernetes puede descargar esa imagen desde el registry. Docker construye/ejecuta contenedores; Kubernetes orquesta Pods y sus réplicas.

Ejemplo de .dockerignore

  node_modules
  npm-debug.log
  .git
  .env
  coverage
  .DS_Store

Evita enviar archivos innecesarios o sensibles al contexto de build. Si excluyes .env, la aplicación debe recibir la configuración por un mecanismo externo al construir la imagen.

5. Diagnóstico de problemas comunes

Síntoma Qué revisar Comandos útiles
Contenedor se detiene Proceso principal, error de arranque, variables, configuración. docker ps -a
docker logs my-api
No conecta el puerto Puerto publicado, puerto interno y que la app escuche en 0.0.0.0 dentro del contenedor. docker port my-api
docker inspect my-api
API no conecta a MySQL Red compartida, hostname del servicio, credenciales y estado de la base. docker compose ps
docker compose logs mysql
No encuentra imagen Nombre/tag, registry, autenticación y arquitectura compatible. docker images
docker pull registry/image:tag
Datos desaparecen Que el directorio de datos esté montado en un volumen o bind mount. docker inspect db
docker volume ls
Build lento o imagen grande Orden de COPY, caché, .dockerignore y multi-stage build. docker image history my-api:v1

6. Buenas prácticas para producción

  • ✔ Usa imágenes oficiales y versiones específicas; evita depender de latest.
  • ✔ Aplica multi-stage builds y mantén pequeño el contexto con .dockerignore.
  • ✔ Ejecuta la aplicación como usuario no root cuando sea posible.
  • ✔ No copies contraseñas, tokens ni archivos .env dentro de la imagen.
  • ✔ Persiste datos importantes en volúmenes o almacenamiento externo.
  • ✔ Usa redes dedicadas y expón solo los puertos necesarios.
  • ✔ Define healthchecks realistas y registra logs en stdout/stderr.
  • ✔ Fija versiones, analiza vulnerabilidades y reconstruye imágenes para recibir actualizaciones de seguridad.
  • ✔ Usa tags inmutables o identificadores de commit en CI/CD.
  • ✔ Revisa el alcance de los comandos de limpieza antes de borrar recursos.
Guía de referencia educativa. Adapta imágenes, puertos, rutas de salud, credenciales y nombres de recursos a tu proyecto. Para producción, sigue las políticas de seguridad de tu organización.
