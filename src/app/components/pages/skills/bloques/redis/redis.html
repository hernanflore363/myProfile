Redis – Architecture & Production Guide

Guía práctica de Redis para caching, sesiones, control de concurrencia, idempotencia y comunicación de alta velocidad en sistemas distribuidos.

Cache

Redis permite almacenar temporalmente información en memoria, reduciendo la latencia y evitando consultas repetitivas contra bases de datos. 

SET user:1001 "Hernán"
GET user:1001

EXPIRE user:1001 3600

TTL user:1001
Use: caching y reducción de latencia

Key-Value

Redis utiliza una estructura de almacenamiento basada en claves y valores, permitiendo accesos extremadamente rápidos para información frecuentemente utilizada. 

SET payment:001 "PENDING"

GET payment:001

DEL payment:001
Use: datos temporales y consultas rápidas

TTL

Permite establecer un tiempo de expiración para las claves, evitando acumulación innecesaria de información en memoria. 

SET session:abc123 "user-1001"

EXPIRE session:abc123 1800

TTL session:abc123
Use: sesiones, tokens y cache temporal

Hash

Los Hash permiten representar objetos y mantener múltiples atributos asociados a una misma clave. 

HSET user:1001 \
  name "Hernán" \
  role "architect"

HGET user:1001 role

HGETALL user:1001
Use: objetos y estructuras simples

Pub/Sub

Redis Pub/Sub permite publicar mensajes en canales y distribuir eventos entre múltiples consumidores. 

SUBSCRIBE payments

PUBLISH payments "payment-created"
Use: notificaciones y comunicación en tiempo real

Distributed Lock

Redis puede utilizarse para implementar mecanismos de exclusión distribuida y evitar que múltiples instancias procesen simultáneamente una misma operación. 

SET lock:payment:001 \
  instance-01 \
  NX \
  EX 30

DEL lock:payment:001
Use: concurrencia e idempotencia

Rate Limiting

Redis permite implementar contadores distribuidos para controlar la cantidad de solicitudes que un cliente puede realizar durante una ventana de tiempo. 

INCR rate:user:1001

EXPIRE rate:user:1001 60

GET rate:user:1001
Use: protección de APIs y control de tráfico

Redis Architecture Flow

  • Client → API
  • API → Redis
  • Redis → Cache Hit
  • Cache Miss → Database
  • Database → Redis
  • Redis → API → Client

Redis + Kafka

  • ✔ Kafka para eventos y comunicación asíncrona
  • ✔ Redis para cache y acceso rápido
  • ✔ Kafka mantiene el flujo de eventos
  • ✔ Redis reduce consultas repetitivas
  • ✔ Ambos permiten desacoplar servicios

Best Practices

  • ✔ Definir TTL para información temporal
  • ✔ No utilizar Redis como base de datos principal sin una estrategia adecuada de persistencia
  • ✔ Controlar el consumo de memoria
  • ✔ Definir políticas de eviction
  • ✔ Utilizar claves con una convención consistente
  • ✔ Evitar almacenar objetos excesivamente grandes
  • ✔ Monitorizar memoria, latencia y conexiones
  • ✔ Utilizar Redis Cluster cuando la escala lo requiera
  • ✔ Implementar alta disponibilidad cuando Redis sea crítico para el negocio
